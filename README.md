# GitLab Dashboard

Дашборд для ревью и отслеживания Merge Requests из GitLab. Удобен, когда проектов несколько и хочется видеть всё в одном месте.

## Возможности

**Триаж** — открытые MR разложены по четырём корзинам:

| Корзина | Что внутри |
|---|---|
| Needs your review | Открытые MR в твоих проектах, которые ты ещё не апрувил |
| You approved | Ты уже апрувил, MR всё ещё ждёт мержа |
| Your open MRs | Твои собственные открытые MR |
| Mentioned you | MR, где тебя упомянули в комментарии |

- Массовые действия: approve / unapprove / re-approve по выделенным MR, с явным отчётом, если что-то не прошло
- По каждому MR: статус пайплайна со ссылкой, аппруверы, ассайни, лейблы, счётчик тредов (resolved/total)
- Треды видно прямо в интерфейсе — превью комментариев, ответы, файл и строка
- В корзине «You approved» подсвечивается активность **после твоего апрува**: новые коммиты, новые треды и новые ответы в старых тредах
- **No merge request** — работа, которую ревью не видело: ветки без MR (с кнопкой создания) и коммиты, легшие в защищённую или дефолтную ветку мимо MR
- **Browse** — merged/closed с поиском, фильтрами и постраничным выводом
- **To-Do List** — GitLab-тудушки с фильтром по типу события и «отметить всё выполненным»
- Несколько аккаунтов GitLab одновременно с переключением между ними
- Фильтр видимых проектов; выбор и фильтры запоминаются отдельно для каждого аккаунта
- Автообновление с настраиваемым интервалом
- **Релизы из Jira** — задачи в нужном статусе, затронутые репозитории, план внедрения и план отката, сборка тега

## Стек

| Часть | Технология |
|---|---|
| Frontend | React 19 + Vite + Tailwind CSS 4 + Radix |
| Backend | Python 3.12 + FastAPI + httpx |
| Запуск | Docker Compose (nginx + uvicorn) |

## Запуск

### Через Docker Compose

```bash
cp .env.example .env      # заполни GITLAB_URL и SECRET_KEY
docker compose up --build
```

Открой `http://localhost:8085` и подключи аккаунт: адрес GitLab + Personal Access Token.

### Локально

**Backend:**
```bash
cd backend
pip install -r requirements.txt
GITLAB_URL=https://gitlab.example.com SECRET_KEY=dev uvicorn main:app --reload
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev
```

Vite проксирует `/api` на `http://localhost:8000`, так что фронт и бэк живут на одном origin.

## Доступ

Токен вводится в самом приложении, а не в конфиге: он шифруется и лежит в httponly-куке сессии.
Нужен Personal Access Token со скоупом `api` (для апрува и тудушек) или `read_api`, если хватает режима только для чтения.

## Конфигурация

| Переменная | Описание |
|---|---|
| `GITLAB_URL` | Адрес GitLab, подставляется в форму входа как значение по умолчанию |
| `GITLAB_DEFAULT_GROUP` | Группа, чьи проекты выбираются автоматически при первом открытии |
| `JIRA_URL` | Адрес Jira Server/Data Center. Превращает ключ задачи из имени ветки в ссылку в анонсе ревью; пусто — в буфер ляжет голый ключ. Вместе с `JIRA_PROJECT_KEY` включает раздел Releases |
| `JIRA_PROJECT_KEY` | Проект Jira, версии которого считаются релизами. Пусто — раздела Releases нет |
| `JIRA_RELEASE_STATUS` | Статус задач, входящих в релиз. По умолчанию `Включено в релиз` |
| `GITLAB_CA_BUNDLE` | Бандл корневых сертификатов для GitLab и Jira. В образе уже задан, см. «Внутренние сертификаты» |
| `SECRET_KEY` | **Обязателен.** Ключ шифрования сессионных кук. Без него сессии сбрасываются при каждом рестарте, а при `SECURE_COOKIE=true` приложение просто не стартует |
| `SECURE_COOKIE` | `true`, когда раздаёшь по HTTPS — добавляет флаг `Secure` к куке |
| `CORS_ORIGINS` | Список origin через запятую. Пусто = CORS выключен (нормальный режим, фронт и API на одном origin) |
| `LOG_LEVEL` | `DEBUG` показывает каждый запрос к GitLab; по умолчанию `INFO` — только медленные (>1s) |

Тонкая настройка нагрузки на GitLab (значения по умолчанию обычно менять не нужно):

| Переменная | По умолчанию | Описание |
|---|---|---|
| `USE_GRAPHQL` | `true` | Тянуть MR через GraphQL: один запрос на пачку проектов вместо трёх REST-вызовов на каждый MR. При любой ошибке молча откатывается на REST, так что выключать не нужно — но `false` пришпиливает старый путь |
| `GRAPHQL_PROJECT_BATCH` | `5` | Проектов в одном GraphQL-запросе — **верхняя граница**, а не фиксированное значение |
| `GRAPHQL_MR_LIMIT` | `50` | MR на проект в одной странице. Не потолок: если у проекта открытых MR больше, остаток дочитывается по курсору (до `MAX_MR_PAGES` страниц) |
| `GRAPHQL_PIPELINE_DEPTH` | `5` | Сколько последних пайплайнов MR запрашивать, чтобы выбрать среди них пайплайн ветки, а не `merge_request_event` |

У GitLab есть потолок сложности запроса (по умолчанию 250), и заранее он неизвестен — зависит от набора запрошенных полей. Поэтому размер подбирается сам: запрос ужимается (`5×50 → 2×50 → 1×50 → 1×25 → 1×10`), пока инстанс его не примет, и рабочий размер запоминается на час. Подбирать константы руками не нужно; текущий выбранный размер видно в `/api/graphql-check` в поле `settled_on`.
| `GITLAB_CONCURRENCY` | `10` | Потолок одновременных запросов к GitLab |
| `CACHE_TTL` | `60` | Сколько секунд живут аппрувы, пайплайны и треды в кэше |
| `APPROVAL_TTL` | `900` | Кэш активности после апрува; инвалидируется по `updated_at` самого MR |
| `UNREVIEWED_TTL` | `600` | Кэш раздела «No merge request». Это самое дорогое чтение в дашборде — перечень веток каждого проекта плюс история живых стволов — а меняется оно, когда кто-то пушит, а не посекундно. Кнопка Refresh кэш обходит |
| `CACHE_MAXSIZE` | `4096` | Потолок записей в каждом кэше (LRU) |
| `MAX_MR_PAGES` | `5` | Потолок страниц на один запрос списка MR (по 100 штук) |
| `MAX_PROJECT_PAGES` | `10` | Потолок страниц при загрузке списка проектов |

Сборка за корпоративным прокси — `REGISTRY`, `PIP_INDEX_URL`, `PIP_TRUSTED_HOST`, см. `.env.example`.

Токен GitLab вводит каждый пользователь при входе. Нужен scope `api`: с `read_api` можно смотреть MR, но approve и действия в To-Do работать не будут. Токен Jira (Personal Access Token) вводится в разделе Releases.

## Внутренние сертификаты

В образ бэкенда встроен `backend/sogaz-ca-bundle.pem`, на него указывает `GITLAB_CA_BUNDLE`. По нему проверяются и GitLab, и Jira. Если нужен другой сертификат, создай рядом с `docker-compose.yml` файл `docker-compose.override.yml` (он не попадает в git):

```yaml
services:
  backend:
    environment:
      GITLAB_CA_BUNDLE: /certs/ca.crt
    volumes:
      - /mnt/c/путь/к/сертификату.crt:/certs/ca.crt:ro
```

Путь указывай так, как его видит оболочка, в которой запускается `docker compose`: в WSL это `/mnt/c/...`, в PowerShell `C:/...`. Запускай без `-f`, иначе этот файл не подхватится. `SSL_CERT_FILE` здесь не действует: `GITLAB_CA_BUNDLE` важнее.

## Сборка тега

Кнопка Build tag в таблице релиза вливает `develop` в `master` (или `main`, если `master` нет) и ставит тег на результат. Перед этим окно показывает, что уйдёт в `master` вместе с тегом: задачи этого релиза, задачи в других статусах, задачи вне релиза и коммиты без задачи. Сборка начинается только после подтверждения.

Само приложение git не запускает, а работает через GitLab API, но окно показывает команды git с тем же результатом, чтобы то же самое можно было сделать вручную. Слияние идёт через merge request, поэтому действуют правила проекта: если нужен approve или зелёный пайплайн, сборка остановится и покажет причину. Повторный запуск продолжит с того же места. Ветка `develop` не удаляется, а если она изменилась после просмотра, слияние не начнётся.

## Как собирается план релиза

1. Версия Jira даёт список задач, из него берутся задачи в статусе `JIRA_RELEASE_STATUS`.
2. У каждой задачи читаются ссылки на GitLab, которые создаёт интеграция GitLab и Jira (mentioned on). Так находятся MR и репозитории.
3. Все теги репозитория читаются из GitLab при каждой сборке плана. Последний тег это самая высокая версия `vX.Y.Z`, а не самый свежий по дате: хотфикс `v4.32.1`, созданный после `v4.33.0`, последним не считается.
4. Для каждого MR проверяется, в какие теги попал его коммит:
   - есть изменения без тега: внедрение это следующая версия (`v1.3.0` → `v1.4.0`), тег ещё нужно создать;
   - всё уже в последнем теге: внедрение это этот тег;
   - всё в более старом теге, а новее есть другие теги: репозиторий по умолчанию не входит в план, это решает человек;
   - тегов `vX.Y.Z` в GitLab нет: версию продолжать не от чего, поэтому тег не предлагается и репозиторий по умолчанию не входит в план.
5. Откат это ближайший тег ниже, в котором нет изменений этого релиза.

Теги можно поправить вручную прямо в таблице перед копированием плана. Фильтр Projects действует и здесь: в планы попадают только выбранные проекты, а остальные перечислены под таблицей. Если ничего не выбрано, показываются все.

## Тесты

```bash
cd backend
pip install -r requirements-dev.txt
pytest
```

Юнит-тесты решают, что каждое правило говорит про один MR, одну ветку или один
коммит. Сквозные — что из запроса получаются правильные вызовы, в правильном
количестве: их обслуживает `backend/fake_gitlab.py`, поддельный GitLab, который
воспроизводит неудобные части настоящего — глобальные id и строковый `iid` в
GraphQL, потолок сложности запроса, постраничные `/projects`, защищённый
`master` рядом с дефолтным `develop` с общей историей.

Его же можно поднять и руками, чтобы потыкать дашборд без доступа к GitLab:

```bash
python fake_gitlab.py     # 127.0.0.1:9911
```

С [direnv](https://direnv.net) окружение поднимается само: `.envrc` экспортирует
`.env` и активирует pyenv-окружение из `.python-version`. После первого клона —
`pyenv virtualenv 3.13.3 gitlab-dashboard` и `direnv allow`.

## Диагностика

Работает ли GraphQL на твоём инстансе — спросить у самого приложения:

```
GET /api/graphql-check?project_id=<id любого доступного проекта>
```

Отвечает `ok: true` и разобранным примером MR, либо `ok: false` с причиной от GitLab.
`cooling_off: true` означает, что запрос недавно упал и ближайшие 10 минут используется REST.
